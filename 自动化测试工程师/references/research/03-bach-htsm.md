# James Bach HTSM — 自动化测试视角提取

> 来源：现有测试工程师技能（James Bach Perspective），聚焦与自动化测试相关的部分

## 核心框架：HTSM 四维度

| 维度 | 问什么 | 自动化测试中的应用 |
|------|--------|------------------|
| **项目环境** | 什么约束影响测试？ | CI/CD 能力、团队自动化技能、工具链、时间压力 |
| **产品元素** | 产品由什么组成？ | API 接口、UI 组件、数据流、平台依赖 |
| **质量标准** | 什么才算"好"？ | 功能性、可靠性、性能、安全性、可维护性 |
| **测试技术** | 用什么方法探测？ | 等价类、边界值、状态转换、组合测试、风险驱动 |

## Testing vs Checking — 自动化定位

- **自动化的是 Checking**，不是 Testing
- Checking = 机械化验证（pass/fail），可完全自动化
- Testing = 开放性调查，需要人类判断力
- 推论："自动化测试"这个说法是误导的——自动化的是 checking
- 关键：自动化负责"已知正确性"，人工负责"未知问题"

### 应用到自动化测试工程师
- TDD 写的 unit test = unit checks（验证已知命题）
- 自动化 UI 检查 = checking（不是 testing）
- 探索性测试 = testing（不可自动化）
- 新技能需明确：自动化 checking + 人工 testing = 完整测试策略

## 风险驱动测试 — 指导"自动化什么"

1. 列出风险列表：什么可能出错？
2. 针对最高风险设计自动化检查
3. 持续调整：旧风险消失、新风险出现时重新分配

**关键启发式**：如果这个功能只测一个场景，测哪个？那个场景就是最高风险场景，应优先自动化。

## 3D 渲染测试（现有资产）

| 维度 | 关注点 | 测试方法 |
|------|--------|---------|
| 视觉正确性 | 光照/材质/阴影准确性 | 自动化 pixel diff（checking）+ 人眼抽样（testing） |
| 性能 | 帧率、GPU内存、draw call | Profiler数据（checking）+ 体感流畅度（testing） |
| 兼容性 | 不同GPU/驱动/分辨率 | 风险驱动：先测最常用+最可能出问题的配置 |
| 交互 | 摄像机、碰撞检测、动画 | 探索性测试高价值区域 |

### 推荐混合策略
- **自动化 checking**：pixel diff、渲染错误日志、性能指标（覆盖 90%+ 场景）
- **人工 testing**：每版本抽样 10-20% 场景进行人眼探索（聚焦高风险/新变更）

## Good Enough Testing — 何时停止自动化投入

检查清单：
- [ ] 是否用 HTSM 四维度扫描过，识别了所有高风险区域？
- [ ] 高风险区域的自动化检查深度是否达到可接受水平？
- [ ] 利益相关者是否已知悉并签署了"已知未覆盖区域"清单？
- [ ] 是否有至少 1 个利益相关者明确表示"这个质量水平可以发布"？
- [ ] 是否记录了"我们选择不自动化什么"及其理由？

## 与自动化测试工程师的定位区分

| 维度 | 测试工程师（Bach视角） | 自动化测试工程师（新技能） |
|------|---------------------|------------------------|
| 核心关注 | 测什么、为什么测 | 怎么测、怎么自动化 |
| 方法论 | 探索性测试、HTSM、风险驱动 | TDD、测试金字塔、CI/CD |
| 人的角色 | 测试者=调查员 | 测试者=工程师 |
| 自动化定位 | checking（有限的） | 核心能力（全面的） |
| 适用场景 | 测试策略设计、质量决策 | 测试工程实现、自动化管线 |

> 两者互补：Bach 管策略（道），新技能管执行（术）
